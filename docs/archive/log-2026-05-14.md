### [session] MENU_CANVAS_ZINDEX_OVERLAP_FIX — PASS (branch: main)

**What changed:** แก้ 2 ปัญหา z-index ที่ทำให้ menu bar dropdown ถูก canvas overlay ทับ: (1) `.menu-bar` ไม่มี `position` → z-index ไม่ทำงาน แก้ด้วย `position:relative` + เพิ่ม z-index เป็น 9000 (2) `#check-panel` ตั้ง `top:var(--topbar-h)` = 22px → บัง menu bar + ribbon ทั้งหมด แก้ด้วย `calc(var(--topbar-h) + var(--menu-h) + var(--ribbon-h))` = 94px. Modal ทุกตัว (setup-overlay, .panel, export-panel, pgmgr-overlay, scale-mgr-overlay) ถูก raise เป็น 9001–9002 เพื่อให้ยังอยู่เหนือ menu-bar ใหม่. loupe + recent-proj-dropdown ลด z-index เป็น 8998–8999 (ต่ำกว่า menu-bar).

**Why:** ผู้ใช้รายงาน "เมนูบาร์ด้านบนโดนเมนูในแคนวาสทับ". สาเหตุหลักคือ `position:static` บน `.menu-bar` ทำให้ `z-index:100` ไม่มีผล — CSS z-index ใช้งานได้เฉพาะ positioned element เท่านั้น. canvas overlay (summary-widget 400, draw-bar 500, ctx-menu 600, obj-picker 700) และ loupe (9999) + recent-proj-dropdown (10000) จึงทับ dropdown ทุกครั้ง.

### [session] PATH_GEOMETRY_VISUAL_AUDIT — PASS (docs-only, branch: main)

**Scope:** Audit-only investigation of every Phase H.1 path geometry surface. No source change. Triggered by user report that circle/curve output looks visually strange even though PATH_GEOMETRY_OK passes.

**What audit found:** Root cause = UI / render integration gap — NOT a geometry bug.

Phase H.1 math is fully correct: `circleToPath`, `ellipseToPath`, `arcToCubic`, `rectangleToPath`, `_flattenCubicSeg`, `flattenPathToPoints`, `pathAreaM2`, `renderPath`, `objectAreaM2` path branch — all verified. Canonical constants correct (`k=0.5522847498`, `(4/3)·tan(|sweep|/4)·r`). `_PATH_FLATTEN_TOL=0.1` produces ~2k points per circle, area error <0.1%. PATH_GEOMETRY_OK passes legitimately.

**But none of the new path API is wired into user-facing tools:**
- `mode==='circle'` handler (`proto/ui.html:1327`) still builds legacy 32-vertex polygon via `_circlePolygonPts(center, radius, 32)`, sets `shape="circle"`. Never calls `circleToPath`, never sets `geometryType='path'`.
- `mode==='ellipse'` same: `_ellipsePolygonPts`.
- `redraw()` (`proto/ui.html:1209`) iterates `mPolys.forEach` using `poly.pts` exclusively — never branches on `poly.geometryType`, never calls `renderPath`.
- `circleToPath`, `ellipseToPath`, `arcToCubic`, `rectangleToPath`, `renderPath` — **zero production callers**. Only called from E2E `_test_path_geometry` via `page.evaluate()` direct invocation.

**Visual symptom explained:** user draws a circle → canvas shows 32-vertex polygon. Area label uses analytic `circleAreaM2(radius)` (correct number). User sees polygonal outline + accurate number → "ตัวเลขถูกแต่รูปดูแปลก". PATH_GEOMETRY_OK bypasses UI entirely; `circle_tool` E2E test mirrors legacy `_circlePolygonPts` flow. **This is NOT a Phase H.1 regression — Phase H.1 scope was model+math+render-function API; UI wiring was explicitly deferred.**
